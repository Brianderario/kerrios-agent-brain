## ITEM 1 — GET /api/v1/deals/:id/renewal_brief

### Phase 1 — BRAINSTORM (23:35 ET)

Approaches considered:

1. **Inline serializer in a new controller action** (mirrors `renewals#index`'s `renewal_json`). Lowest ceremony, but the proof_points + owed-breakdown logic is meatier than a flat row and deserves isolated unit tests. Rejected as the home for the logic.
2. **Model method on Deal** (like `fulfillment_summary`). Bloats an already-large model with view-shaped assembly; harder to test in isolation. Rejected.
3. **Service object `Crm::RenewalBrief`** returning the structured hash, with a thin controller action. Matches the existing `Crm::DealHealth` / `Crm::HygieneScorer` pattern exactly, purely additive (new file), directly unit-testable, no blast radius on existing code. **CHOSEN.**

Data audit (all associations confirmed to exist, real-data-only):
- `newsletter_placements` → `delivered?` (delivered_on OR issue published+past), `delivery_status`, `committed?`, `newsletter_issue` (issue_date, display_name).
- `case_file_entries` → kind, occurred_on, summary, source.
- `account_signals` → `engagement?` subset (ENGAGEMENT_SIGNAL_TYPES), signal_type, subject, occurred_at, strength.
- `contract_deliverables` → contracted_count, delivered_count, owed_count, delivery_status.
- `contracts` → `already_signed?`/signed/active → `papered?`.
- `fulfillment_summary` → {contracted, delivered, owed}; `renewal_days_left`, `renewal_status`.

No invented numbers: every receipt string is a count of real rows; a deal with no signal emits an empty `proof_points` array. `owed_before_renewal` is derived from the same committed-placement + contract-deliverable sets `fulfillment_summary` already uses, with each line carrying its record id.
