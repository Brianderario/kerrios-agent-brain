## ITEM 1 — Crm::SignalFeed service

### Phase 1 — BRAINSTORM (07:50 ET)

**Approaches evaluated:**

A. **Pure SQL aggregate in the service** — Group `account_signals` by `company_id`, take `MAX(occurred_at)` as `most_recent`, `COUNT(*)` as `signal_count`, order by `most_recent DESC, signal_count DESC`. Then eagerly load company, recent signals (top N), open deals. No new table, no invented score — only real signal rows and real deal rows.

B. **In-memory sort** — Load all signals for the org, group by company in Ruby, sort. Clean but could be slow on large sets; also can't efficiently push the ranked company_ids to a separate deals query.

C. **Materialized view** — Pre-aggregate in the DB. Requires a migration (creates a view), more schema surface, overkill for read-only reporting.

**Rejected:** C (new schema surface, violates "no new table" constraint). B (N+1 risk on large signal sets; SQL group-by is cleaner and DB-indexed).

**Chosen: Approach A.** SQL aggregate over the passed-in `account_signals` relation, one query for the ranked list, one preloaded query for the recent signals per company, one join for open deals. All real data.

**Pundit scope:** Controller passes `policy_scope(@organization.account_signals)`. Requires a thin `AccountSignalPolicy` with a Scope that:
- Full members see all org signals except those linked to a deal in a blocked restricted event (mirrors DealPolicy::Scope).
- This is the spec's "restricted-event access carries through" requirement.

**Prospect status derivation:** No `prospect_status` column on Company. Derive from:
- Any open (non-closed) deal → stage of most-advanced deal
- No open deal → "no deal"

**Done definition:** Service returns correct ranked data (most-recent-signal company first), spec covers ranking + prospect status + Pundit scope exclusion, rubocop + brakeman clean, full rspec green.
