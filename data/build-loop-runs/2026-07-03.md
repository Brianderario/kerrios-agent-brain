### Item 1 — read_mail_attachment (BRAINSTORM + PLAN)
Approaches considered: (a) new read-only tool that downloads the email attachment via the existing `download_attachment` on both mail clients and extracts text with the existing shared `FileTextExtractor` (PDF/.docx) + the Slack::AttachmentReader text-MIME/ext table; (b) extend `read_mail` to inline attachment text automatically (rejected: bloats every read, blows token budgets on big PDFs, no per-attachment control); (c) OCR/vision for image attachments (rejected: new dependency + model capability KMG doesn't have wired; park). Chose (a): zero new dependencies, reuses two proven components, read-only, and directly closes the observed Xometry-PSA gap ("I can't extract the text content from a .docx email attachment"). Registration points: tools.rb MAIL_TOOL_NAMES (so Oliver's mail-off config disables it), SUBAGENT_TOOL_NAMES (read-only), definitions, schema; tool_executor TOOL map + EXTERNAL_TOOLS + handler; one additive system-prompt line. Done = the agent can be asked "read the PSA Madison attached" and the tool returns the document text (verified by specs + prod deploy + read-only prod smoke of the tool executor via specs, no live DM).
Plan: schema {mailbox, message_id, attachment_name|attachment_id, max_chars}; handler guards mailbox access, downloads (10MB cap), dispatches by content_type/extension → FileTextExtractor.pdf/.docx or UTF-8-scrubbed text; returns name/content_type/size/text/truncated; clear error for images/binaries. Specs: executor happy paths (pdf, docx, text), unsupported binary, guard denial, name-miss error passthrough.
