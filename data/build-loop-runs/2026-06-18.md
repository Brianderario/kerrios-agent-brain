## ITEM 1 — GET /api/v1/deals/:id/deal_brief (Crm::DealBrief)

### Phase 1 — BRAINSTORM (23:35 ET)
Three approaches considered:
1. **Mirror RenewalBrief as a sibling service `Crm::DealBrief`, thin controller action on DealsController, member route.** Reuses DealHealth + stakeholder + engagement records directly; one source of truth shared with Item 2's screen. Blast radius: additive only (new service, new action, new route). CHOSEN.
2. Extend RenewalBrief to handle open deals with a mode flag. Rejected: overloads a shipped, tested service used by the renewals screen — risks regressing the renewal path; muddies a clean abstraction.
3. Compute the brief inline in the controller. Rejected: can't be reused by Item 2's screen (the task requires one source of truth for screen + API), and untestable in isolation.

Data check (all real, on-record): identity from deal columns + `stage_changed_at`/`last_activity_at`; stakeholders from `deal_stakeholders`→person; engagement (sent/opened) from `account_signals` engagement types (proposal_sent/proposal_viewed, contract_sent/contract_viewed); deal_health from `Crm::DealHealth`; proof_points from delivered placements + case-file entries + engagement signals (same three the renewal brief emits); to_advance from DealHealth `reasons` (weak factors) + engagement-derived "sent N days ago, not opened". No invented numbers; null stays null; empty arrays when no signal. Decision: serve the brief for any deal in the org (do NOT hard-reject closed) — strictly additive/robust, symmetric with renewal_brief which doesn't reject open deals; the screen only feeds it open gap-closers. `stage` + `open` fields tell the consumer.
