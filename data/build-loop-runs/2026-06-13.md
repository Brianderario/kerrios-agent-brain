## ITEM 1 — Delivery status on existing newsletter placements

### Phase 1 — BRAINSTORM (chosen approach + rejected)

**Chosen:** Add nullable `delivered_on` (date) to `newsletter_placements` (the record that carries the booking). Add derived, non-stored `delivery_status` on the model: `delivered` (delivered_on set, OR issue is published AND issue_date is in the past — i.e. the placement ran) / `owed` (committed [deal-linked or sold] AND not delivered AND not cancelled) / `cancelled` / `unsold` (uncommitted inventory). New additive read endpoint `GET /api/v1/deliverables?status=owed` (deals:read) returning owed placements with deal, sponsor, scheduled date, soonest-first, with `?deal_id=` filter. UI: an "Owed" tab on the existing newsletter inventory surface + an owed-vs-delivered line on the deal page. Backfill `delivered_on` only source-backed: Dirac's 6 published primaries (set to their issue_date). Zero change to existing sold/open/reserved derivation.

- *Why:* `delivered_on` on the placement is the smallest additive change; the booking already lives on `NewsletterPlacement`. Derivation (not a stored status column) means no drift and no migration of existing status values. "Ran" is keyed off the ISSUE being published + past (reliable) rather than the placement's own workflow status (import-default-dependent), so delivered-detection is robust.
- *Rejected:* (a) a new `placement_deliveries` join table — overkill, the date belongs on the placement. (b) Storing a `delivery_status` enum column — would drift from reality and risks colliding with the existing `status` workflow enum; derivation is truthful by construction. (c) Backfilling delivered_on for all 42 published reserved placements — only Dirac is source-confirmed by Brian's ad-calendar reconciliation; the rest still correctly derive as delivered (past+published) without an invented explicit date.

### Phase 2 — PLAN

2. Migration `backfill_dirac_delivered_on` — set `delivered_on = issue_date` for Dirac primary placements in published past issues where delivered_on IS NULL (raw SQL join, idempotent, source-backed). Reversible no-op down.

## ITEM 2 — Non-newsletter contracted units as first-class deliverables

### Phase 1 — BRAINSTORM (chosen + rejected)

**Chosen:** New `ContractDeliverable` model (uuid pk) linked to a deal: `kind` enum (fireside_chat, company_spotlight, event_booth, event_dinner, other), `contracted_count`, `delivered_count`, optional `delivered_on`, `source` (SOW reference), `notes`. Derived `delivery_status` (delivered when delivered_on set or delivered_count ≥ contracted_count; else owed) + `owed_count`. Append-only API `GET/POST /api/v1/deals/:id/deliverables` via a distinct controller `Api::V1::Deals::DeliverablesController` (index = deals:read, create = deals:write; NO update/destroy routes, so the record stays trustworthy). Deal page gains a "Contracted deliverables" section.

- *Why a new model, not the existing `Deliverable`:* the existing `Deliverable` is an event-sponsor checklist item (category + pending/in_progress/completed workflow + required `name`, editable via web). ITEM 2's units are count-based SOW obligations, append-only, with owed/delivered derivation. Overloading would force incompatible columns + a synthesized name onto a model with different semantics, and muddy the existing deal "Deliverables" section. The invocation explicitly permits "additive model or enum." A separate, clearly-documented model is cleaner and append-only-safe. Distinct controller avoids colliding with ITEM 1's top-level `Api::V1::DeliverablesController`.
- *Rejected:* (a) extend existing `Deliverable` with kind/counts — semantic muddle + name NOT NULL. (b) reuse ITEM 1's `DeliverablesController` for the nested route — conflates newsletter placements with contracted units on one controller.
