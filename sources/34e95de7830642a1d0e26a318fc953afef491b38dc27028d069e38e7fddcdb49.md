# iMessage Handoff (Claude Code)

Skill at `~/.claude/skills/imessage-handoff/` lets Brian text iMessage to continue a Claude Code session. Triggered by `/imessage-handoff`, "start handoff", "stop handoff", or "continue this from iMessage".

**Architecture:** Ported from [gragland/codex-imessage-handoff](https://github.com/gragland/codex-imessage-handoff). Stop hook fires on each turn → publishes last assistant text to Cloudflare relay → opens WebSocket → on inbound iMessage, prints `{"decision":"block","reason":"<text>"}` to stdout to inject the reply as the next user turn.

**Shared infra with Codex install:**
- Relay: `imessage-handoff.brian-08a.workers.dev` (Brian's own Cloudflare Worker)
- Token + paired phone: copied from `~/.codex/skills/imessage-handoff/.state/config.json` via `configure.js set-config-from`
- Same Sendblue number receives messages for both Codex and Claude Code threads. Text `threads` to the number to list active ones across both apps; text a number to switch.

## CRITICAL: mid-turn progress updates during long handoff tasks

When responding to an iMessage handoff reply that triggers a long task (multi-step tool use, web research, large refactors, sub-agent spawns), **run `send-update.js` at the start of the work and every ~2 minutes**:

```bash
node ~/.claude/skills/imessage-handoff/scripts/send-update.js \
  --session-id="$CLAUDE_CODE_SESSION_ID" \
  --message="Brief one-sentence status"
```

The continuation prompt the Stop hook injects includes this command pre-built; just copy and run it. Without these heartbeats, the iMessage user sees silence during long turns (because the Stop hook only fires AFTER Claude stops), which feels like the conversation "fell off."

## iMessage style rules

iMessage renders markdown as raw characters. When answering an iMessage handoff turn: prose only, brief, no headers/tables/bullet lists/code fences unless user explicitly asked for code. One or two paragraphs.

## Debug log

Hook events log to `~/.claude/skills/imessage-handoff/.state/hook.log` (JSONL, rotates at 512KB). Read this when a handoff conversation falls off — it records every fire, publish, wait-start, inject, and error.

## Fix log

- **2026-06-01 — final answer arriving one turn late on long tasks (off-by-one delivery).** Claude Code's Stop hook stdin (unlike Codex's `input.last_assistant_message`) does NOT include the assistant text, so `publish-stop.js` re-reads it from the JSONL transcript. The old logic took the *last assistant text in the whole file* and broke on the first non-empty read; on a long turn the final block flushes a beat after the hook fires, so it grabbed the *previous* turn's answer. The relay suppresses an unchanged message, so that turn sent nothing and the real answer only went out on the next turn ("right answer, but only after I texted again"). Fix: new `readCurrentTurnAssistantMessage()` in `common.js` scopes to assistant text *after the current turn's user message* (and skips tool-result rows, which Claude logs as user-type, as boundaries); `publish-stop.js` also rejects any read equal to the persisted `lastPublishedMessage` (in `active-threads.json`) and extends the retry budget to ~6s, falling back to sending rather than dropping. Takes effect on the next hook fire — no Claude Code restart needed (the hook re-reads the script each invocation). Verified via syntax check, 8 unit tests, and real-transcript extraction. `hook.log` now records `sawStaleMatch` to confirm the dedup is firing.

## Known limitations

- Image MMS receive not implemented (gragland has it for Codex; not yet ported)
- No local-takeover detection: if Brian types in Claude Code while hook is waiting, the iMessage reply still wins the next turn. Workaround: `/stop-handoff` from another session, or Ctrl-C + `/stop-handoff`.
