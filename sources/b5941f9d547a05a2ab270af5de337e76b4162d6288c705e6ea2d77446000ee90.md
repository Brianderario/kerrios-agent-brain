**Kerri's self-upgrade loop kept dying on large files (2026-07-02, six failed turns on the create_deal upgrade).** THREE root causes in `kerrihq-rails`; the first two fixed in PR #309 (merge c37dfcf, live 15:57 UTC), the third caught by the live QA loop on her next attempt and fixed in PR #310 (merge 0af5912):

1. `search_code` returns line numbers but `read_code_file` only accepted character offsets; no conversion existed, so she paged 80K-char chunks through her context until older reads got stubbed. Fix: `read_code_file` takes `start_line`/`end_line` (1-based), whole-line slices, verbatim content, `next_start_line` on overflow. `CodeContext#read` line mode wins over offset.
2. `CodeContext#read` encoded binread (ASCII-8BIT) to UTF-8 with `undef: :replace, replace: ""`, silently DELETING every multi-byte character (em dashes, curly quotes). Copied `old_string`s never matched the file, so `ship_code` failed "old_string not found". Fix: `force_encoding(UTF-8)` + `scrub` only when invalid.
3. The agent's read-suppression guard (`AskSavant::Agent#guarded_code_read_result`) keyed every read by `[path, offset]`; line-range calls default offset to 0, so the first line read of a file suppressed ALL later line reads of that file as "repeated". Also line-mode results polluted the char-coverage map (nil offset coerced to 0). Fix: `code_read_key` keys line reads by `[path, :lines, start, end]`; line results skip the coverage map; line reads exempt from fully-read suppression.

**Why:** Brian's active project is Kerri making functional upgrades to herself; anything that corrupts her read-copy-edit loop silently blocks it.
**How to apply:** if Kerri reports she "can't reach a section" or ship_code says old_string not found, suspect tool-layer fidelity FIRST, and QA by comparing a read against the file byte-for-byte (that's how the UTF-8 bug was caught).
