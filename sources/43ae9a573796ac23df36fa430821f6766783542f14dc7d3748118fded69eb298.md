**Incident (2026-07-02):** a Render deploy restart at 12:54 UTC killed an in-flight Slack agent turn; session `slack:T09UJ7NHRK2:D0B3TBA0U3Z:main` stayed `active` holding a dead AgentTask and Brian's next message (12:57, before Solid Queue wrote the ProcessPrunedError prune record) queued forever until a manual nudge. PR #304 only released on prune-marker + new inbound event, so that ordering was unrecoverable.

**Fix: PR #308** (`kerrihq/kerrihq-rails`), **MERGED + DEPLOYED + VERIFIED ON PROD 2026-07-02** (merge commit bf32cf6, live on both Render services ~13:57 UTC; sweep confirmed ticking every 2 min in queue-worker logs from 14:02, no errors):
- `Slack::SessionRecovery.release_stale_active_task!` (renamed from `release_pruned_active_task!`) releases on prune marker OR no-live-Solid-Queue-execution (dead/gone worker heartbeat, all job rows finished) OR 30-min runtime ceiling; also unpins sessions pointing at already-finished tasks.
- `SlackSessionRecoverySweepJob` recurring every 2 min (`config/recurring.yml`) releases stuck sessions and kicks the queue head with no inbound event; also re-kicks idle sessions with orphaned queued tasks (5-min grace). Worst-case recovery ~7 min (5-min `SolidQueue.process_alive_threshold` + 2-min sweep).
- `SessionQueue#schedule_if_idle` kicks the oldest queued task (FIFO), not the newest.

**PR #312 (merge d8499891, live + synthetically verified on prod 2026-07-02 ~19:54 UTC): worker-killed turns auto-rerun.** SessionRecovery requeues a killed message once when (a) the release reason is worker death (not the runtime ceiling), (b) the dead turn only used read-only tools (whitelist = `AskSavant::Tools::SUBAGENT_TOOL_NAMES` + read-only orchestrator tools, read from progress events' `metadata.tool`; anything else, e.g. reply_mail/update_deal/ship_code, blocks retry to prevent double-execution), and (c) it isn't already a retry (`metadata.retry_of`). The clone keeps original created_at for FIFO. Trigger incident: Brian bulk-merged ~9 dependabot PRs 18:50-19:27 UTC = deploy every ~4 min, killing Kerri's turns repeatedly; sessions released fine (PR #308) but messages were lost. Bulk PR merges during work hours strafe in-flight agent turns; batch them or expect auto-retries.

**Why:** deploy restarts are routine on Render; a stuck session silently eats Brian's Slack messages.
**How to apply:** if a Slack session looks stuck on prod, check `AgentSession` status + the sweep's log lines (`[SlackSessionRecoverySweepJob]`) before manual surgery; released tasks carry `output.stale_reason`. The old uncommitted local WIP on that branch was byte-identical to merged PR #304 (no lost iteration).

**Render deploy retry:** a `build_failed` deploy showing `fatal: could not read Username for 'https://github.com'` in build logs is a transient Render↔GitHub clone flake (seen 2026-07-02 on the queue worker while the web service built the same commit fine). Fix: `POST /v1/services/<srv>/deploys` with empty JSON body retries the latest commit; the previously live version keeps serving in the meantime.
