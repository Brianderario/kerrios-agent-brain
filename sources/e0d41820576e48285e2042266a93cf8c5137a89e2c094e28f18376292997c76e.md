When Brian directs an email **send from chat** (riffing/editing a draft live with Kerri, outside the inbox-sweep approval-card flow), after the send succeeds Kerri MUST immediately find and close the matching Console/Savant approval task so it cannot be approved again and double-send.

**Why:** Brian likes drafting and editing in chat because it is faster than the queue. But the draft usually already has a `needs_approval` card filed by an earlier sweep. If that card is left open, Brian (or a later sweep) can approve it and send a second, stale copy. Source: ChipAgents H0187, 2026-06-15 (Brian rule).

**How to apply (hardened 2026-06-17 — use the ONE atomic command, never the hand-steps):**
```
node scripts/console-task-api.mjs close-job --job <jobId> --message-id <id> --note "<what/where it went>"
```
This single call closes the send card (`done`/`sent_interactively`), closes the paired recap card (from the job's `routing.recapCardId`), logs the `sent` receipt, verifies the card reads `done`, THEN flips the `data/jobs.json` job (`status`/`resolution`/`sentAt`/`sentMessageId`). It is **card-first** so a partial failure can never leave a re-approvable card behind, **idempotent** (safe to re-run), auto-selects the open job for that jobId (pass `--card <consoleTaskId>` if duplicates are ambiguous), and supports `--dry-run`. This replaces the old four-step hand sequence (list → update → event → edit jobs.json), which is what allowed the 2026-06-17 half-completion: an interactive send flipped jobs.json to sent but left both cards in `needs_approval`, re-sendable ~12h (C-Infinity H0119 + Protolabs H0106 + Kickstarter H0154). See [[feedback_brain_log_check_before_send]] and the no-double-email rule.

**Do NOT use `mark-applied` for this** — that path is the sweep acknowledging its own approved send. **Safety (built into `close-job`):** `--status done` fires a task's server-side `on_complete` only when the payload is non-blank AND resolution is not `skipped`; queued email-reply cards carry a blank `on_complete`, so closing is side-effect-free. If a card DOES carry a non-blank `on_complete` (e.g. `create_deal`) whose effect you already did by hand, `close-job` refuses rather than double-firing it — re-run with `--resolution skipped` (or `update --clear-on-complete` first).
