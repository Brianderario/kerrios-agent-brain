**2026-07-09 OUTAGE + model switch:** Kerri in Slack was answering "I could not put together an answer for that" on nearly every request. Root cause: `glm-5.2` on ollama.com degraded — it dumps all output into the OpenAI `reasoning` field and returns `content: ""` with `finish_reason:"length"` (reasoning eats the whole token budget), or sometimes 200 with `completion_tokens:0`. ~2 of every 3 requests came back blank → `AskSavant::Agent` `empty_model_response` fallback (`app/services/ask_savant/agent.rb`, message at `app/services/slack/event_processor.rb`). The `ASK_SAVANT_MODEL_FALLBACKS` chain did NOT rescue it because `OllamaClient.chat` only fails over on HTTP *errors* — a blank-but-200 response is treated as success. **Fix applied:** flipped `ASK_SAVANT_MODEL` glm-5.2 → **`glm-5.1`** on both Render services (web `srv-d8kvn767r5hc739fjo9g` + queue `srv-d8kvnkcvikkc73c8cm6g`); fallbacks glm-5.1,deepseek-v4-pro → `gpt-oss:120b,glm-5` (dropped deepseek — same empty-response tool bug per research). Chosen after empirically testing 11 models on the live endpoint (tool-calling + 2nd-hop chain + reliability + heavy-context stress): glm-5.1 = 0 empty failures under production-scale context, ~8s, calls tools decisively; qwen3.5 flaked 1/5 empty; gpt-oss reliable but under-calls tools (talks instead of acting). **Durable fix SHIPPED (PR #475, branch `harden/ollama-empty-200-failover`, 2026-07-09):** `OllamaClient` now detects a blank-content-200 with no tool calls (`blank_completion?`), retries once with a bumped `max_tokens` + `reasoning_effort:"low"`, and if still blank raises a retryable `empty_response` Error that drives the `ASK_SAVANT_MODEL_FALLBACKS` chain. Tool-call turns (blank content + tool_calls) are excluded so the agent loop is unaffected. Reasoning field is logged, never used as the final answer. Full suite green (4063 ex, 0 failures). Once merged+deployed, glm-5.2 can safely return as primary because the harness auto-recovers from this degradation; team may also just stay on glm-5.1.

Brian's Slack/Savant agent model strategy (set 2026-07-07, PRs #451/#452). Analogy he gave: **GLM-5.2 = his Opus** (daily driver: conversation, direct asks, actions), **kimi = his Sonnet** (the lighter model the harness delegates grunt work to). He grants judgment on how to split them.

- **Primary / driver = `glm-5.1`** (`ASK_SAVANT_MODEL` env; was `glm-5.2` until the 2026-07-09 outage above): conversation, direct asks, the action/orchestrator loop, plus the `strong` and `code` tiers (which fall back to `ASK_SAVANT_MODEL`). Also `balanced` = `glm-4.7` (context-condensing), unchanged.
- **Fast / delegate tier = `kimi-k2.6`** (`ASK_SAVANT_MODEL_FAST` env = kimi-k2.6, live on both Render services; code default also kimi-k2.6). Used for grunt work: context-compaction summaries + `delegate_to_model 'fast'` (extraction/summarizing/condensing).
- **kimi runs at LOW reasoning effort** (`ModelTiers.effort_for(:fast)` = "low", env `ASK_SAVANT_MODEL_FAST_EFFORT`): kimi-k2.6 is a REASONING model that burns ~600 tokens thinking on a trivial task at default effort; "low" cuts that ~2.4x (~269 tokens) with same accuracy. Threaded via `OllamaClient.text(reasoning_effort:)`. Scoped to fast tier only; glm-5.2 keeps full reasoning.

Config lives in `app/services/ask_savant/model_tiers.rb` (`TIERS`, `EFFORTS`, `model_for`, `effort_for`). Ollama endpoint = `https://ollama.com` (OpenAI-compatible).
