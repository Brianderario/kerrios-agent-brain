# Savant Build Learnings

scope: workflow · created: 2026-06-17

The code-side learnings store for Savant ([[../properties/savant]] / `kerrihq-rails`). The compound step of the build loop ([[../../../agent-prompts/build-loop/SKILL.md]] Phase 6) appends here after every item, and reads this page during brainstorm so past lessons shape new work before any code is written. This is the [[compound-engineering]] two-tier model in practice; it is the code-side sibling of [[draft-learnings]] (email).

Two kinds of entry live here, and they age differently:

- **Learning** = one solution to one past problem (a bug fix, a convention discovered, a workflow that worked). Incident-level. Append freely; never edit an earlier entry.
- **Pattern doc** = a rule generalized from several Learnings. Higher leverage, higher risk when stale. Promote a Learning into the Patterns section only after several incidents point the same way, never from a single case. Review Patterns for freshness; Learnings need no upkeep.

## Learning format

```
## [YYYY-MM-DD] <module/area> — <one-line title>
**Problem:** what broke or was unclear, with the production evidence.
**Fix:** what was actually done (commit SHAs welcome).
**Lesson:** the durable takeaway the next agent should carry, in one or two sentences.
**Tags:** area keywords for retrieval (e.g. migrations, authz, api-compat, n+1, deploy).
```

Keep each entry plain enough that Don could read it cold and a future agent could grep it. The date lives in the entry, not a filename.

## [2026-06-18] crm/deal_brief — building an "analog" reporting service the right way
**Problem:** Needed an open-deal advancing brief as the analog of the shipped `Crm::RenewalBrief` (GET /api/v1/deals/:id/deal_brief), reusing the 6/13 DealHealth + stakeholder + engagement records without re-deriving anything or inventing numbers.
**Fix:** New `Crm::DealBrief` mirroring RenewalBrief's exact shape — same payload envelope, same `proof_points` builder spirit (one plain line per non-zero count, correctly pluralized), same null/empty discipline — and REUSING `deal.health_summary`, `deal.deal_stakeholders`, and `account_signals` engagement scope. `to_advance` = DealHealth `reasons` (the weak factors) + an engagement-derived "Proposal/Contract sent N days ago, not yet opened" from the proposal_sent/proposal_viewed signal pair. Thin controller action on DealsController + member route, gated `deals:read`. Commit 79e9395.
**Lesson:** When you build an analog of an existing reporting service, mirror the sibling exactly and reuse its scorer/associations rather than recomputing — the screen and the API stay one source of truth and the phantom-data discipline comes for free. Three concrete gotchas, all real here: (1) a nested hash embedded for a web view needs `.transform_keys(&:to_s)` or ERB (symbol keys) and JSON (string keys) read it differently — RenewalBrief already does this for `fulfillment_summary`; follow that precedent for any embedded hash. (2) `Deal#days_in_stage` returns `0` (not nil) when `stage_changed_at` is blank — if you want "null stays null," compute nil-safe in the service, don't reuse the model method. (3) The `track_stage_change` before_save CLOBBERS `stage_changed_at` + `last_activity_at` to `Time.current` on create, so factory-set timestamps don't stick; use `update_columns(...)` after create to age a deal in specs.
**Tags:** crm, services, api-compat, deals, deal-health, specs, factories, phantom-data, [[draft-learnings]]

## [2026-06-18] revenue/pipeline-worklist — zero-JS expandable worklist + DealBrief reuse
**Problem:** Needed a Pipeline worklist screen (open gap-closing deals: proposal_sent/negotiation/contract_sent, ranked value DESC then most-aging) under the existing Revenue nav, with each row expandable to its advancing brief, overflow-safe and with no new top-level surface.
**Fix:** `PipelineController` mirroring `RenewalsController` (read-only, Pundit org-show gate, preload the brief's associations to avoid N+1, order `value DESC NULLS LAST, stage_changed_at ASC`), a view reusing the renewals idioms (panel + `overflow-x-auto` table + native `<details>/<summary>`), and `@briefs = Crm::DealBrief` per deal so the screen and GET /deal_brief never drift. Web route `get "pipeline"` beside `get "renewals"`; one nav link added in the Revenue group. Commit 790424b.
**Lesson:** The renewals worklist's native `<details>/<summary>` + `overflow-x-auto`-wrapped table is the proven zero-JS, overflow-safe idiom for an expandable worked screen — reuse it wholesale, including the system spec that asserts `document.documentElement.scrollWidth <= window.innerWidth` at both 1440 and 390, collapsed AND expanded. Reuse the row's data service so the screen and API are one source of truth. Two gotchas: (1) rubocop chokes if you pass it an `.html.erb` path directly (it parses the template as Ruby → hundreds of false "offenses") — ERB is not a rubocop target, lint only `.rb` files and trust the project-wide `bin/rubocop` run. (2) A new link inside an existing nav group is NOT a "new top-level surface"; label it distinctly from any existing item (here the existing "Pipeline" = the deals kanban, so the new screen is "Pipeline worklist" at /pipeline) and key `nav-item-active` on its own path segment so the two don't both light up.
**Tags:** revenue, ui, views, system-specs, n+1, pundit, rubocop, nav, deals, [[draft-learnings]]

## [2026-06-18] pwa/mobile-shell — served PWA files are not installability
**Problem:** Savant had PWA routes, manifest links, and mobile meta tags, but the signed-in shell did not actively register the service worker or expose stable app shortcuts. The backlog item was "shipped" as a baseline, but phone use still felt like a responsive site instead of an installable app.
**Fix:** Added a small Stimulus `pwa` controller to register `/service-worker.js` and mark browser vs standalone display mode; enriched the manifest with `id`, `display_override`, portrait orientation, categories, and shortcuts; added redirect-only top-level shortcuts for Tasks, Approvals, Pipeline, and Events; replaced the placeholder worker with a conservative public-asset cache that never stores authenticated HTML. Commit cc03f7f.
**Lesson:** PWA work is not done when Rails serves `/manifest.json` and `/service-worker.js`; the authenticated shell must register the worker, manifest shortcuts need stable non-org-scoped routes, and private console pages must stay network-only. In Rails ERB JSON templates, use `raw path.to_json` for path helper values or the response can emit HTML entities such as `&quot;` instead of valid manifest strings.
**Tags:** pwa, mobile, stimulus, manifest, service-worker, auth, privacy, specs

**Problem:** Brian asked Kerri to become S-tier at two writing capabilities (B2B sales email/proposal and the S&W newsletter) and wire the craft into the agents. (4) Wire craft through ONE referenced page the routines load, not by bloating each routine prompt; and make the editor/critic wiring flag-don't-fabricate so a critic never invents an unsupported "so what" against the freshness/accuracy bar.

## [2026-06-18] ui/design-system — re-skin the whole app by evolving shared tokens + the @layer components block
**Problem:** Brian wanted the dense "Palantir terminal" Savant reskinned to a calm editorial "Monaco" look (near-black canvas, serif display, violet->magenta accent, pill nav) across all ~15 screens, with data unchanged. Screen-by-screen first would be slow and inconsistent.
**Fix:** Evolved the FOUNDATION only and let it propagate: `tailwind.config.js` tokens (ink ramp -> near-black neutral; accent blue -> violet `#8161FF` + new `magenta`; add `Newsreader` serif family) + the `@layer components` block in `application.tailwind.css` (softened `.panel` radius; new `.display/.eyebrow/.pill*/.btn-white/.ask-bar/.glass`) + the shell serif wordmark. Because every screen reuses `.panel/.console-btn/.microlabel/.nav-item/.badge/.kanban-*/status-dot` + the accent token, one foundation change re-skinned the entire app; the Overview was then reworked as the flagship (serif greeting hero + Ask bar that opens the command palette). Commit d4ddfda, live + prod-verified (`/up` 200; compiled CSS carries the violet gradient + Newsreader).
**Lesson:** When an app's look is centralized in Tailwind tokens + a small `@layer components` block, ship a "foundation" item first (tokens + shared classes + shell) and the whole app moves at once; later items become editorial polish, not re-theming. Gotchas, all real here: (1) self-host webfonts exactly like the existing Inter/IBM faces (`woff2` in `app/assets/fonts`, `@font-face url('name.woff2')`) — Propshaft resolves it by precedent; the screenshot proved the serif painted before deploy. (2) `app/assets/builds/*.css` is gitignored and rebuilt at deploy (cssbundling precompile), so commit the SOURCE (`tailwind.config.js` + `application.tailwind.css`), not the build. (3) Tailwind v3 emits utility colors as `rgb()` channels, not hex — verify a token reached prod CSS by its raw-CSS hex (e.g. a gradient) or the rgb triple, not the utility's hex. (4) Sentence-casing a literal uppercase ERB string (e.g. "NEEDS YOU" -> "Needs you") breaks request specs that assert the old literal — grep `spec/` for the string before changing copy. Verify a behind-login redesign with a seeded system spec that screenshots at 1440 + 390 and asserts `document.documentElement.scrollWidth <= window.innerWidth`.

## [2026-06-18] pipeline/kanban — whole-card drag + SortableJS fallback (native DnD was the bug)
**Problem:** Brian reported deal drag "doesn't work" on the pipeline. Two causes: the deals board used SortableJS handle-only drag (a tiny grip), so grabbing the card body just opened the deal; and it used native HTML5 drag-and-drop (`forceFallback: false`), which intermittently started no drag lifecycle at all. The server side was fine throughout (`update_stage` is covered by green request specs).
**Fix:** `kanban_controller.js` now uses whole-card drag on every board plus SortableJS's mouse-event fallback (`forceFallback: true` + `fallbackTolerance: 5`), keeping `delayOnTouchOnly` so a plain click still opens the card. JS-only; the tasks board already used the whole-card gesture, so it is unchanged. Commit 76b520b.
**Lesson:** (1) When a SortableJS board "won't drag," suspect native HTML5 DnD before the server: `forceFallback: true` (mouse-driven) is far more reliable across browsers and devices and is the default to reach for. (2) Handle-only drag is a footgun on cards that are also click-to-open; whole-card drag + `fallbackTolerance` gives both. (3) VERIFYING a drag: the chrome-devtools `drag` tool / CDP drag do NOT drive SortableJS reliably (native or fallback). What works is dispatching the real pointer sequence via `evaluate_script` (pointerdown, pointermoves past tolerance over a container found by `elementFromPoint`, pointerup) and asserting the DB stage changed, plus replaying the controller's exact PATCH (`fetch` with `X-CSRF-Token` + `Accept: text/vnd.turbo-stream.html`) to prove the round-trip. (4) TEST-DB HYGIENE: a throwaway SYSTEM spec left rows that leaked into transactional specs and produced 24 phantom failures (`create(:user, email: <fixed>)` collisions, `Membership` global-scope `contain_exactly`). Purge with `RAILS_ENV=test bin/rails db:test:prepare`, and delete scratch screenshot/triage specs before a full-suite gate; never leave a non-transactional spec in `spec/system` as scratch.
**Tags:** pipeline, kanban, sortablejs, stimulus, drag, ui, system-specs, test-db, verification, [[draft-learnings]]

Changing that wrapper string breaks the `pwa_spec` assertion that pins it — update it. (4) Verify the UI round-trip in a real browser even without the key: the no-key path returns the friendly error, proving panel -> POST (CSRF) -> controller -> agent -> render; the real answer is verified in prod (proven model) or by the human's prod login.

## [2026-06-19] ask-savant/ollama — run the in-app agent on Ollama (GLM-5.2), not Anthropic
**Problem:** The Anthropic API key was never configured in prod (verified via a prod one-off: credentials hold only `secret_key_base/active_record_encryption/tito`; no `ANTHROPIC_API_KEY` env). Brian asked about OAuth-through-his-Claude-subscription (not available for a custom server app) and then supplied an Ollama key to run the agent on instead.
**Fix:** Added `OllamaClient` (Ollama hosted, OpenAI-compatible chat at `https://ollama.com/v1/chat/completions`, Bearer key) and rewrote `AskSavant::Agent` + `Tools` from the Anthropic shape to the OpenAI tool-call shape: `tools=[{type:function, function:{name,description,parameters}}]`; read `choices[0].message.tool_calls`; append the assistant message with `tool_calls`, then one `{role:"tool", tool_call_id:, content:}` per call; loop while `finish_reason=="tool_calls"`. `ToolExecutor`/`SystemPrompt`/controller/route/UI unchanged. Model `glm-5.2` (tool-calling verified), `ASK_SAVANT_MODEL` overridable. Key set as Render env var via single-var PUT. Commit 42ce4c3.
**Lesson:** (1) OAuth/subscription auth is for Anthropic's first-party clients (Claude Code), NOT a custom server app calling the Messages API (that is API-key + metered). The SDK's value is agent ergonomics, not free subscription usage. (2) Swapping LLM providers is cheap when the agent is layered: a thin client + a tool-schema/loop adapter changed; `ToolExecutor` (real data access) + controller + UI did not. Keep that seam. (3) Anthropic vs OpenAI tool shapes differ: Anthropic = `input_schema` + content blocks (`tool_use`/`tool_result`-as-user); OpenAI/Ollama = `function.parameters` + `message.tool_calls` + `role:"tool"` with `tool_call_id`. (4) Use Ollama's HOSTED endpoint (`ollama.com`), not local — Render can't reach a Mac's localhost. (5) Render single-env-var update is `PUT /v1/services/{id}/env-vars/{KEY}` `{value:...}`; the BULK `PUT /env-vars` replaces the whole set and would wipe `DATABASE_URL`/`RAILS_MASTER_KEY` — never use it without every existing value. (6) Since the key was local + the service is cloud, the real end-to-end answer was verifiable BEFORE deploy (`rails runner` -> real GLM-5.2 answer), unlike the keyless Anthropic path.

## [2026-06-19] access/multi-user-matrix — siloed access + permission-aware agent (the big one)
**Problem:** Stand up real multi-user access on Savant — a strict visibility matrix (own tasks fully siloed both ways incl. the owner; pipeline for Brian/Ari/Benji not the external partner Zach; the Ironclad S/W event for Brian/Ari/Zach not Benji) — and make the in-app Ask Savant copilot respect it AND act within it. Security is the deliverable; fail-closed; must NOT break the `/api/v1` inbox-sweep automation.
**Fix:** Shipped as 7 small commits (635c35e foundation → f64be54 tasks → 398caa5 pipeline → ceb28c5 Ironclad → 87b994f provision → aa39801 agent reads → 98df743 agent actions) + a critical fix (8de18c5). Topology was decisive: production is SINGLE-org (HFYI/S&W are Domains, not orgs; Ironclad is an events row), so everything is restricted-data-WITHIN-one-org. Single source of truth = `User#can_see_pipeline?`/`can_see_event?` (item 1) reused by policies + nav + the agent tool layer. Tasks siloed by flipping `Task.visible_to` to strict `assignee=user` (one scope flips board+dashboard+approvals+ConsoleStatus/Today+agent at once) + a backfill migration + default-assignee on the API-create/health-job so nothing orphans. Ironclad = `events.restricted` flag + EventAccess as the allow-list, gated by two shared `ApplicationPolicy` helpers (`event_visible?` + Scope `without_blocked_restricted_events`, Arel/no-SQL-strings) applied to Event/Deal/SponsorshipOption/TicketSearch/TicketSale. Agent: opened to event_guests but every read tool scoped (pipeline via DealPolicy::Scope, brain full-members-only via PermissionResolver, tasks siloed); slice-2 actions (update_deal preview→confirm, create/update_task own-workspace) each authorize via the SAME Pundit policy + write an AgentRun audit in one transaction. Verified by ONE comprehensive `spec/requests/access_matrix_spec.rb` (4 factory roles, +/- every cell), full suite 1696/0, + a real glm-5.2 e2e action, + a read-only prod one-off dumping the live matrix.
**Lesson:** (1) **The agent must enforce the SAME policies as the UI/API, keyed on current_user** — call the Pundit policy/Scope classes directly in the tool executor (`DealPolicy::Scope.new(@user, scope).resolve`, `DealPolicy.new(@user, deal).update?`); don't reinvent. (2) `EventAccess`/`event_guest` is an ADDITIVE allow-list for OUTSIDERS — it cannot SUBTRACT one event from a full member without demoting them org-wide. To hide an event from a full member, add a `restricted` flag and require an explicit access row even for full members (a new gate on the full-member branch), leaving the event_guest branch unchanged. (3) **`ApiPolicyContext` (the `/api/v1` actor) is NOT a User** — when you add a `User` capability predicate that policies call (`can_see_event?`), you MUST add it to `ApiPolicyContext` too (return true within its org) or the API 500s. The full suite WON'T catch this unless a test record is restricted — add that regression test. (4) Tasks had a nil-assignee leak (`visible_to` included `assignee: nil`); strict siloing means backfilling existing nulls + defaulting every creation path (API create, AgentHealthCheckJob) to the org owner, else cards vanish from every human board. (5) Owner ≠ super_admin: Brian is org owner, `super_admin?` is false — restricted-event gating that only bypasses on super_admin still applies to the owner, so grant the owner an explicit allow-list row. (6) Inside `module AskSavant`, `Agent` resolves to `AskSavant::Agent` (the loop class), not the `::Agent` model — use `::Agent` for find_or_create; the executor's blanket rescue masks such NameErrors as `{error:}`, so a spec asserting `[:ok]` is what surfaces them.

## [2026-06-19] infra/seeds-vs-migrations — db:seed does NOT run on an existing prod deploy
**Problem:** Items 4+5 put the matrix DATA (flag Ironclad restricted, demote Zach to event_guest, EventAccess allow-list) in `db/seeds.rb`, believing the memory's claim "seeds run on every deploy via render.yaml preDeploy." After deploy, a read-only prod one-off showed the data had NOT landed: Ironclad still unrestricted, Zach still a full member — i.e. the deployed policy code had nothing to act on, so the matrix was NOT enforced despite green deploys.
**Fix:** Moved the provisioning into a guaranteed-to-run **migration** (`ProvisionTeammateAccess`, idempotent, ILIKE-matches the prod event, no-op on dev/test). Redeployed → the migration ran in preDeploy → the prod one-off then showed the full correct matrix. Also reverted a seed line that force-set Ari/Benji to `:member` (prod had manually promoted them to admin; forcing member would have demoted them + stripped DealPolicy#update?/deal-edit).
**Lesson:** Render's preDeploy `db:prepare` runs **migrations every deploy** but only runs **`db:seed` on a FRESH database** — so seed-based changes are a NO-OP on the existing prod DB. Any DATA that must reach production (flags, role changes, join rows, backfills) belongs in a **migration**, not seeds (seeds are for provisioning a fresh DB + the local dev/test idempotent baseline). This corrects the prior brain belief; the tasks:resolve backfill precedent (migration, not seed) was right for exactly this reason. ALWAYS verify a data change actually landed with a read-only prod one-off (`POST /v1/services/{id}/jobs` running `bin/rails runner`, then read the JSON line from the JOB's logs via `GET /v1/logs?resource=<jobId>` — NOT the service resource, whose logs are the web workers). And never force a role in an idempotent provisioner — preserve manual elevations.
**Tags:** infra, migrations, seeds, render, deploy, db-prepare, provisioning, verification, prod-one-off, [[draft-learnings]]

## [2026-06-19] ops/worktree-isolation — running a build loop while another Claude session shares the repo

## [2026-07-03] agent/tool-args — valid non-object tool JSON crashed the whole run
**Problem:** Agent#parse_arguments only special-cased UNPARSEABLE JSON; valid non-object JSON ("[]","5","true") reached ToolExecutor#execute and raised NoMethodError on transform_keys OUTSIDE any rescue, 500ing the copilot / discarding a Slack run's work. GLM emits this occasionally.
**Fix:** parse_arguments returns :invalid_json unless the parse is a Hash, routing into the existing 'resend valid JSON' retry; belt-and-braces coercion in execute. PR #336.
**Lesson:** Any place that JSON.parse model output then treats it as a Hash needs an is_a?(Hash) guard, not just a ParserError rescue — providers emit valid-but-wrong-shape JSON. Route it into the model's self-correction path, don't silently coerce to {} (that drops intent).

## [2026-07-03] perf/n+1 — a read-model badge queried once-per-row on every page render
**Problem:** TaskQueueHealth#agent_done_without_proof_count loaded every done agent task and ran a per-task task_events EXISTS query — an unbounded N+1 on every page render (topbar badge), growing with done-task count.

## [2026-07-03] safety/confirmation-gate — incidental words authorized real sends
**Problem:** The coded send gate read a compose-request 'reply' as a send directive (COMPOSE_CONTEXT only tempered EMAIL_WORDS), and matched a bare 'yeah'/'ok' anywhere, so 'draft a reply for me to review' and a mid-paragraph affirmative both authorized an external send.
**Fix:** Split STRONG vs SOFT send verbs (soft suppressed under compose context, strong always authorize); a bare affirmative only counts on a short (<=48 char) message. Fail-safe: can only convert a would-be send into a preview. PR #338.
**Lesson:** A keyword-based authorization gate must (1) suppress verbs that double as compose nouns when the message is a draft request, and (2) treat a bare affirmative as a go-ahead only when the message IS essentially that confirmation, not when it's buried in a longer instruction. Every tightening here is fail-safe (more previews), so bias toward suppression.
